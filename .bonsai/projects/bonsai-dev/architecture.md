# Architecture

**Project:** `bonsai-dev`  
**[Meta: Human-owned | Target Implementation Truth | Rebuild-Grade | No Execution Plans]**

## Goal and Overview

**Architectural Goal:** Introduce one small shared workspace seam for projects and maps while preserving concrete project/map identities, project-specific execution semantics, map-specific source-navigation behavior, and Bonsai's existing specification-first progressive-discovery model.

**System Overview:** `specification.md` remains the authoritative Bonsai framework truth. Repository-local `.bonsai/start.md` establishes repository and Bonsai Home identity, resolves the active project or map workspace, loads that workspace's small `workspace.md`, and delegates to `<bonsai-home>/prompts/implementation.md`. The implementation kernel reconstructs common workspace state from `agent_plan.md` and `agent_state.md`, then routes to project-specific or map-specific behavior. Projects retain requirements, architecture, phase planning, final-truth reconciliation, contracts, icebox behavior, and other project-only workflow. Maps gain repository-local resumable execution memory, optional scoped detailed plans, map-specific handoff/reconciliation, and generation or maintenance of reusable map output stored in the active map store.

**Approved Principles:**

- `specification.md` is the authoritative human-owned Bonsai framework truth.
- Standard prompts, skills, templates, category guides, and bootstrap files implement the specification.
- Projects and maps are the only current concrete workspace types.
- Shared workspace behavior exists only where both types genuinely need the same lifecycle mechanics.
- Project-specific phase, final-truth, contract, and review behavior remains project-specific.
- Map-specific source inspection, map generation, map/source identity, and mapping completion behavior remains map-specific.
- Workspace memory and generated reusable map output have different ownership even when Embedded Bonsai causes physical path overlap.
- Active workspace identity is session state, never a persisted mutable pointer.
- Framework context remains progressively discoverable and lazily loaded.
- Completed Artifact Discovery work remains part of the active standard architecture, not a new implementation target.

## Domain, State, and Flows

- **Workspace:** Repository-local durable unit of resumable agent work. Concrete type is `project` or `map`.
- **Workspace Entry:** Small human-readable declarative `workspace.md` that identifies workspace type and routes implementation behavior.
- **Workspace Roadmap:** `agent_plan.md`; common role is roadmap-level work decomposition and current status. Project plans may include phases; map plans include mapping units and may delegate large units to scoped detailed plans.
- **Workspace Resume State:** `agent_state.md`; common role is current objective, readiness, blockers, active detailed plan if any, exact next step, success condition, and only other facts that materially change resumption.
- **Project Detailed Plan:** `plan/agent_plan_phase_<N>.md`; project-specific phase execution artifact governed by project planning/review rules.
- **Map Detailed Plan:** Flat scoped files such as `plan/agent_plan_baja.md` or `plan/agent_plan_baja_lang.md`; map-specific execution decomposition that does not become a project phase.
- **Map Calibration:** Optional human-owned `map_calibration.md` expressing source-specific mapping emphasis and guidance; not execution state and not generated output.
- **Generated Map:** Reusable source-navigation knowledge in the active map store, normally entered through `code_map.md` and related subsystem/index files.
- **Project Map Association:** Durable project operational context listing reusable maps that are useful to that project.
- **State / Persistence:** Project and map execution memory persists repository-locally. Project final truth persists under project memory. Map calibration persists with the map workspace. Reusable generated maps persist in the active map store. Active workspace identity and fresh-session auto-execute authorization are session-local and are not persisted.
- **Startup Flow:** Human invokes repository-local `.bonsai/start.md` -> bootstrap resolves repository and Bonsai Home -> resolves project or explicit map identity -> loads selected `workspace.md` -> invokes implementation kernel -> kernel loads minimal execution state -> routes by workspace type -> presents or bypasses only the startup gate according to the retained request. | **Failure Handling:** Invalid Bonsai Home, nonexistent explicit workspace, ambiguous project selection, missing/invalid workspace entry, inconsistent state, or a mandatory gate must be surfaced rather than guessed around.
- **Project Execution Flow:** Project startup -> reconstruct shared workspace state -> load project truth and project-specific workflow as required -> phase planning/execution/final-truth/contract gates operate under existing project rules -> shared handoff reconciles common state plus project-specific state -> next action is continued now, in a fresh session, changed/reviewed, or exited. | **Failure Handling:** Shared workspace behavior must not bypass project-specific human gates.
- **Map Execution Flow:** Explicit map startup -> reconstruct map roadmap/state and active detailed plan if any -> load mapping skill and only needed source/map context -> inspect authoritative source -> update/reconcile generated map output -> maintain map plan/state -> shared handoff reconciles common state plus map-specific output/source identity -> continue or complete current mapping scope. | **Failure Handling:** Stale or incompatible map/source identity, insufficient source evidence, or no safe exact next action blocks continuation; do not substitute project semantics.
- **Fresh-Session Continuation Flow:** Handoff establishes one concrete agent-performable exact next action with no independent decision gate -> human chooses fresh-session auto-execute -> prompt carries workspace identity but no rendered volatile step detail -> new session reconstructs canonical durable state -> executes only the one exact next action -> authorization expires at the next natural gate. | **Failure Handling:** Any newly discovered gate, inconsistency, blocker, or absence of a safe exact next action stops execution.
- **Map Creation Flow:** Web UI design/calibration -> `create_map.md` -> package repository-local `.bonsai/start.md` plus map `workspace.md`, `agent_plan.md`, `agent_state.md`, and optional `map_calibration.md` -> coding-agent mapping later generates reusable output. | **Failure Handling:** Creation must not fabricate `code_map.md`, subsystem maps, or lookup tables.
- **Project Creation Flow:** Web UI project design -> `create_project.md` -> package canonical bootstrap plus project `workspace.md` and project memory -> Phase 1 planning remains first implementation gate. | **Failure Handling:** Creation must not begin implementation or generate the detailed Phase 1 plan.
- **Project Map-Association Flow:** Human manages code maps -> project context gains or loses selected map identities -> future project sessions use those selections as operational context. | **Failure Handling:** Association changes must not mutate generated map content or active workspace identity.

## Cross-Cutting Constraints

- **Runtime / Build Assumptions:** Standard artifact identities are expressed relative to `<bonsai-home>`. Embedded mode resolves `<bonsai-home>` to repository-local `.bonsai`; reusable-home mode may resolve elsewhere. The repository being mapped may itself be unrelated to the Bonsai Home.
- **Error / Recovery:** Missing workspace entries, inconsistent execution state, stale map/source identity, invalid generated-map references, dangling category-guide references, or stale superseded artifact names must be surfaced and corrected rather than silently tolerated.
- **Concurrency:** Active workspace identity is session-local so separate AI sessions may operate on different projects or maps in one repository. No mutable global current-workspace pointer is introduced.
- **Security / Integrity:** Workspace routing documents and category guides cannot grant authority beyond `specification.md`. Project/map operational context must not contain secrets. Source remains authoritative over generated map descriptions.
- **Observability:** Validation should make workspace resolution, roadmap/state agreement, map/source identity, generated-output ownership, stale-name removal, and category-guide/reference integrity directly inspectable.
- **Extension / Configuration:** The shared workspace seam is intentionally proven only by projects and maps. Do not add a generic type registry, arbitrary third type, nested map-plan tree, or Faber dependency without a concrete later requirement.

## Guardrails and Questions

- **Implementation Guardrails:** Preserve ordinary unqualified project startup behavior; require explicit map identity for normal map resume; keep `workspace.md` small and declarative; keep volatile continuation in `agent_state.md`; keep map detailed-plan files flat under `plan/`; do not store map execution state in generated map output; do not add compatibility aliases for renamed creation prompts or retired map-state artifacts unless a concrete compatibility requirement emerges; update category guides when standard artifact names/responsibilities change.
- **Architecture Guardrails:** Shared workspace code and documentation must branch into project- or map-specific behavior rather than flattening their domain semantics; repository-local workspace memory and Bonsai Home generated maps remain conceptually separate in all modes; progressive discovery remains intact; the live `bonsai-dev` project may remain in its pre-`workspace.md` physical shape only until the implementation introduces the new contract.
- **Explicitly Rejected:** Generic `.bonsai/workspaces/`; generic empty workspace creation; generic workspace plugin/type registry; treating map plans as project phases; nested map-plan directory trees in this work; storing active workspace selection in agent context; generated map `map_state.md`; map-state templates; Faber-backed requirements/architecture; personal/work Bonsai Home layering; broad speculative redesign beyond the approved specification.
