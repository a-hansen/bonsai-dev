# Requirements

**Project:** `bonsai-dev`  
**[Meta: Human-owned | Current Product Truth | Bounded Scope | No Implementation Detail]**

## Product Goal and Problem

**Goal:** Evolve Bonsai from a project-centric execution model into a workspace model where projects and code-mapping efforts are both first-class, resumable repository-local workspaces while preserving the project behavior and progressive-discovery capabilities that already work.

**Problem:** Bonsai can persist project implementation work across fresh sessions, but code mapping still has a separate, weaker lifecycle. Large mapping efforts can outgrow one session or even one module-sized unit, yet mapping execution state is not modeled with the same durable plan/state and handoff semantics as projects. Startup, implementation routing, handoff, creation workflows, and map storage also reflect this asymmetry. Without a shared workspace seam, future map work risks large chat context, duplicated lifecycle logic, and continued special cases such as `map_state.md`.

**Primary Users:** Bonsai contributors and software engineers using AI coding agents to implement projects or map substantial source repositories across fresh sessions.

## Outcomes and Workflows

**Core Outcomes:**

- Projects and maps are the two concrete Bonsai workspace types and share the lifecycle mechanics that genuinely apply to both.
- A project continues to behave like a Bonsai project, including project-specific final-truth, phase, contract, and review semantics.
- A mapping effort can be planned, paused, resumed, handed off, and automatically continued in a fresh session without relying on chat history or `map_state.md`.
- Repository-local map workspace memory remains distinct from reusable generated map output.
- Large mapping scopes can be decomposed into smaller detailed mapping plans when needed.
- Projects can explicitly retain which reusable code maps are useful to them.
- Bonsai retains specification-first progressive discovery and lazy context loading.

- **Resume project work:** Human starts Bonsai normally or selects a project -> Bonsai resolves the project workspace -> reconstructs current project state -> routes through project-specific planning/execution behavior -> stops at the next applicable gate. | **Failures:** Map-specific behavior must not weaken or replace project phase, final-truth, contract, or review gates.
- **Resume map work:** Human starts with `Active map: <map>` -> Bonsai resolves the map workspace -> reconstructs its roadmap, state, and active detailed plan if any -> continues mapping or stops at the next real gate. | **Failures:** Bonsai must not guess an unqualified startup means a map or require chat history to know the next mapping step.
- **Continue in a fresh session:** At a natural project or map handoff, Bonsai records the exact next step and readiness -> human chooses fresh-session continuation -> the new session reconstructs durable state and automatically executes only that one exact next action when no independent gate blocks it. | **Failures:** Auto-execute must stop when reconstruction finds a mandatory human gate, inconsistency, blocker, or no safe exact next action.
- **Map a large source:** Agent follows the map-wide roadmap -> decomposes an oversized mapping unit into a scoped detailed plan when useful -> updates generated map output -> reconciles workspace state and output -> continues across sessions until the selected mapping scope is complete. | **Failures:** Detailed map plans must not become project phases merely because they live under `plan/`.
- **Use maps from a project:** Human associates reusable map identities with a project -> Bonsai preserves those selections in project operational context -> future project sessions can load relevant maps without rediscovering the entire map store. | **Failures:** Association changes must not create, rebuild, move, or delete generated maps.

## Functional Requirements

- **FR-1 — Two concrete workspace types:** Bonsai must treat projects and maps as the two concrete resumable workspace types. | **Acceptance:** Repository-local workspace memory remains under `.bonsai/projects/<project>/` and `.bonsai/maps/<map>/`; no generic repository-level `workspaces/` hierarchy is introduced. | **Details:** `None`
- **FR-2 — Workspace entry document:** Every project and map workspace must have a small declarative `workspace.md` entry document that identifies the workspace type and routes the implementation kernel to applicable workspace behavior. | **Acceptance:** `workspace.md` does not contain volatile execution state; plans, readiness, blockers, and exact next steps remain in agent-owned execution memory. | **Details:** `None`
- **FR-3 — Shared execution memory:** Projects and maps must both use `agent_plan.md` as the workspace-wide roadmap and `agent_state.md` as current resume state. | **Acceptance:** Both workspace types can preserve exact-next-step resumption and execution readiness without introducing map-specific state files. | **Details:** `None`
- **FR-4 — Workspace-aware startup:** `.bonsai/start.md` must resolve Bonsai Home, repository home, and active workspace identity, load the selected `workspace.md`, and hand off to the implementation kernel without eagerly loading full workspace knowledge. | **Acceptance:** Explicit `Active project: <project>` and `Active map: <map>` forms work; ordinary unqualified startup retains project-oriented default selection and does not infer a map merely because maps exist. | **Details:** `None`
- **FR-5 — Session-local workspace identity:** Active project or map selection must remain current-session identity rather than a persisted mutable pointer. | **Acceptance:** Concurrent sessions can operate on different workspaces without writing an active-workspace selection into project memory, map memory, developer context, or agent context. | **Details:** `None`
- **FR-6 — Shared handoff lifecycle:** `handoff.md` must operate on the active workspace and provide shared reconciliation and continuation behavior for both projects and maps. | **Acceptance:** Both workspace types support current-session continuation, fresh-session one-step auto-execution, review/change of the next step, and `Exit for now` when applicable. | **Details:** `None`
- **FR-7 — Project semantics remain project-specific:** The shared workspace seam must not force project phase, final-truth, durable-contract, icebox, or related project-specific semantics onto maps. | **Acceptance:** Project workflows retain their current gates and truth model; map handoff and execution invoke only map-applicable reconciliation. | **Details:** `None`
- **FR-8 — Repository-local map execution memory:** Mapping execution memory must live with the source repository under `.bonsai/maps/<map>/`. | **Acceptance:** Map `workspace.md`, `agent_plan.md`, `agent_state.md`, optional `map_calibration.md`, and optional detailed plans are repository-local rather than stored as generated reusable map output. | **Details:** `None`
- **FR-9 — Reusable generated map separation:** Generated reusable source knowledge must remain in the active Bonsai map store and remain conceptually separate from map workspace execution memory. | **Acceptance:** `code_map.md`, subsystem maps, lookup tables, indexes, and comparable generated artifacts are treated as map outputs rather than resume-state artifacts, including when Embedded Bonsai causes physical path overlap. | **Details:** `None`
- **FR-10 — Scoped map planning:** A map workspace must be able to create optional detailed plans under `plan/` when a mapping unit is too large for useful roadmap-level execution. | **Acceptance:** `agent_plan.md` remains the map-wide roadmap; flat scoped plan files such as `plan/agent_plan_baja.md` or `plan/agent_plan_baja_lang.md` may refine large units; `agent_state.md` identifies the active detailed plan and exact next step. | **Details:** `None`
- **FR-11 — No project-style phase requirement for maps:** Detailed map plans must be scoped mapping plans rather than project phases. | **Acceptance:** Creating or refining a map plan does not automatically create project-style phase approval, contract, or final-truth gates. | **Details:** `None`
- **FR-12 — Map completion and reactivation:** A map workspace must support `Complete` when its current selected mapping scope is exhausted and generated output is reconciled, without implying the map can never need work again. | **Acceptance:** Later source changes, maintenance requests, or expanded scope can reactivate the same map workspace. | **Details:** `None`
- **FR-13 — Retire `map_state.md`:** Bonsai must remove `map_state.md` and `map_state_template.md` from the active mapping model. | **Acceptance:** Standard prompts, skills, templates, tests, and guidance no longer create or maintain `map_state.md`; continuation uses map `agent_plan.md` and `agent_state.md`. | **Details:** `None`
- **FR-14 — Simplified creation workflows:** The standard project and map creation prompts must be `prompts/create_project.md` and `prompts/create_map.md`. | **Acceptance:** Project creation establishes `workspace.md` plus project memory while preserving existing project-design synthesis behavior; map creation establishes a resumable repository-local map workspace and does not generate reusable map outputs. | **Details:** `None`
- **FR-15 — Project-to-map associations:** A project must be able to add and remove explicit useful-map selections in project `agent_context.md`. | **Acceptance:** Future project sessions can reuse selected map identities without searching the entire map store; changing an association affects project operational context only. | **Details:** `None`
- **FR-16 — Preserve progressive discovery and lazy loading:** The workspace refactor must retain the existing specification-first artifact-discovery model and avoid making new workspace artifacts permanent context cost. | **Acceptance:** `specification.md` remains authoritative, category guides remain routing aids, bootstrap remains small, and detailed workspace/map/project artifacts are loaded only when required. | **Details:** `None`
- **FR-17 — Validate both workspace types:** The implemented standard must validate project and map startup, shared handoff, map planning, map ownership boundaries, project-map associations, creation workflows, and retired artifact names. | **Acceptance:** Automated and/or focused validation covers the cases defined by the approved specification and catches stale references to superseded mapping and creation artifacts. | **Details:** `None`

## Rules and Constraints

- **Core Concepts:** A workspace is a repository-local durable unit of resumable agent work; `workspace.md` is its stable declarative entry; `agent_plan.md` and `agent_state.md` are shared execution memory; projects and maps remain concrete user-facing concepts; generated maps are reusable source knowledge rather than workspace state.
- **Behavioral Rules:** Startup resolves identity before loading knowledge; explicit workspace identity is authoritative for the session; unqualified startup remains project-oriented; fresh-session auto-execute authorizes one reconstructed exact next action only; shared lifecycle behavior must branch into project- or map-specific rules only where those rules genuinely apply.
- **System Constraints:** Preserve Bonsai Home and Embedded Bonsai modes; keep standard artifact identities relative to `<bonsai-home>`; retain the existing category-guide/artifact-index mechanism; do not require a generic workspace registry or generic workspace directory.
- **Quality Requirements:** The refactor must reduce duplicated lifecycle behavior without hiding ownership boundaries, must remain inspectable in ordinary Markdown, must support fresh-session recovery from durable state, and must keep startup and routine context loading small.

## Scope and Decisions

- **Out of Scope / Non-Goals:** Generic `workspaces/` storage; arbitrary third workspace types; generic empty-workspace creation; a workspace plugin/type registry; nested map-plan directory trees; Faber-backed project truth; making Bonsai depend on Faber; personal/work Bonsai Home layering; generalized Bonsai Home hierarchy; redesign of requirements/architecture as spaces; compatibility aliases for renamed prompts or retired `map_state.md` artifacts without a concrete compatibility requirement.
- **Accepted Decisions:** Keep user-facing `projects` and `maps`; use `workspace.md` as the shared entry seam; share handoff, plan/state, readiness, and fresh-session continuation; keep project-specific phase/final-truth semantics separate; require explicit map identity for normal map resume; use optional flat scoped map plans for further decomposition; keep map workspace memory repository-local and generated map output in the active map store; store project map selections in project `agent_context.md`; rename `create_project_memory.md` to `create_project.md` and `create_map_calibration.md` to `create_map.md`; retire `map_state.md`.
- **Foundational Open Questions:** `None`
- **Open Questions:** `None`

## Definition of Done

This work package is complete when the active Bonsai standard conforms to the approved workspace-refactor specification: projects and maps both operate as resumable workspaces through `workspace.md`, shared plan/state, startup reconstruction, handoff, and fresh-session continuation; project-specific semantics remain intact; mapping uses repository-local execution memory with optional scoped detailed plans and separate reusable generated output; `map_state.md` is retired; project/map creation workflows and project map associations are updated; documentation/category guides/reference integrity are reconciled; and validation demonstrates both project and map workflows without stale superseded artifact names.
